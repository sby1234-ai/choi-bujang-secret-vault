# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.

## 2단계: 자료를 코드 밖으로 (2단계 기록)

가상 메모 네 건은 이제 코드·정적 파일이 아니라 학습용 Supabase 테이블 `notes`에 있습니다. 테이블은 `db/notes.sql`로 만들고, RLS를 켰으며 anon·authenticated에는 권한을 주지 않았습니다. 메모 자체는 SQL Editor에서 한 번 넣었고, 공개 저장소에는 메모 문장을 남기지 않았습니다. 화면(`public/index.html`)은 `/api/notes`(서버 함수 `api/notes.js`)를 통해서만 메모를 읽습니다. `data.json`과 `public/data.json`에는 메모가 없습니다(`"notes": []`).

### 다시 실행하는 방법

1. Supabase SQL Editor에서 `db/notes.sql`을 실행해 테이블을 만들고(이미 있으면 그대로 둡니다), 가상 메모는 SQL Editor에서 직접 입력합니다.
2. Vercel 프로젝트의 Settings > Environment Variables에 `SUPABASE_URL`과 `SUPABASE_SECRET_KEY`를 직접 입력합니다. 값은 코드·Git·채팅에 적지 않습니다.
3. 변경을 푸시하면 Vercel이 다시 배포합니다. 환경변수를 새로 넣었다면 Redeploy가 필요합니다.

### 2단계 당시 남은 약점 (3단계에서 로그인 확인으로 막음)

- 2단계의 `/api/notes`는 공개 주소여서 누구나 가상 메모를 읽을 수 있었습니다. 3단계에서 서버가 로그인 토큰을 검사하도록 바꿨습니다.
- 서버 전용 키는 이 함수만 환경변수로 읽습니다. 키를 브라우저 파일·응답·로그에 넣지 않습니다.

### 메모가 밖으로 새지 않았는지 확인하는 방법

배포 주소는 `https://choi-bujang-secret-vault-eight-psi.vercel.app`입니다. PowerShell에서 실행합니다.

1. 배포된 정적 파일: `/data.json`과 첫 화면 어디에도 메모 문장이 없어야 합니다. 메모 한 건에서 뽑은 짧은 단어를 `찾을단어` 자리에 넣어 검색합니다. 결과가 비어 있으면 통과입니다.

```powershell
curl.exe -s https://choi-bujang-secret-vault-eight-psi.vercel.app/data.json
curl.exe -s https://choi-bujang-secret-vault-eight-psi.vercel.app/ | Select-String "찾을단어"
```

2. GitHub 최신 파일: 저장소 폴더에서 메모 단어를 검색합니다. 아무것도 나오지 않으면 통과입니다.

```powershell
git grep -n "찾을단어"
```

3. 결과 기록 방법: 검색 결과(없음 또는 나온 파일 이름)와 아래 남은 약점을 각각 적어 둡니다. `npm run bundle`의 직접 점검 항목(`public_data_json_read`, `anonymous_api_read`)도 실제로 보낸 요청의 결과만 담습니다.

### 지난 공개 이력은 해소되지 않았습니다

옛 공개 커밋(`Initial commit`)과 1단계 때의 옛 배포에는 가상 메모가 그대로 남아 있습니다. 최신 파일에서 메모를 지웠다고 해서 과거에 노출된 사실이 없어지지는 않으므로, 과거 노출은 해소됐다고 볼 수 없습니다. 실제 자료였다면 이력 삭제와 키 교체가 따로 필요합니다.

### 2단계 기록의 남은 약점 정리

- 로그인 없이 `/api/notes`를 호출하는 약점은 3단계에서 막았습니다(아래 3단계 참고).
- 옛 공개 커밋과 옛 배포에는 가상 메모가 그대로 남아 있습니다.

## 3단계: 진짜 로그인을 붙입니다 (3단계 기록)

Supabase Auth 이메일·비밀번호 로그인과 로그아웃 화면이 있고, 서버가 요청의 로그인 토큰을 검사한 뒤에만 메모 API가 응답합니다. 로그인한 계정은 가상 메모를 추가·수정·삭제할 수 있습니다. 로그인 화면은 공식 SDK(`signInWithPassword`, `signOut`)만 쓰고, 비밀번호나 토큰을 직접 만들지 않습니다. 화면 코드에는 공개용 주소와 publishable 키만 있고 서버 전용 키는 없습니다.

### 3단계 당시 작동하던 기능

- 로그인하지 않으면 화면에 메모가 보이지 않고, 로그인하면 내 메모 목록과 새 메모 입력창이 나타납니다.
- 서버 함수는 틀이 준 `src/verify-login.mjs`로 `Authorization: Bearer` 토큰을 검사합니다. 토큰이 없거나 검사에 실패하면 자료 없이 `401`로 거부합니다.
- 소유자 ID(`owner_id`)는 서버가 검사한 토큰의 사용자 ID로만 저장합니다. 요청 본문에 보낸 `owner_id`, `userId`, `role`은 읽지 않습니다.
- 목록 GET은 로그인한 사용자의 메모만 배열로 돌려줍니다. 2단계에서 넣은 가상 메모 네 건은 소유자가 비어 있어 목록에 나오지 않습니다.

### API (실제 경로는 `aleph.config.json`의 `allowedRoutes`와 같습니다)

| 요청 | 하는 일 | 응답 |
|---|---|---|
| `GET /api/notes` | 로그인 사용자의 메모 목록 | `[{id,title,body}]` |
| `POST /api/notes` | 메모 추가. 본문 `{id?,title,body}` (`id`는 UUID, 없으면 서버가 만듭니다) | `201 {id}`, 같은 id면 `409` |
| `GET /api/notes/:id` | 메모 한 건 | `{id,title,body}`, 없으면 `404` |
| `PUT /api/notes/:id` | 메모 수정. 본문 `{title,body}` | `{id,title,body}` |
| `DELETE /api/notes/:id` | 메모 삭제 | `204`, 지운 뒤 GET은 `404` |

### 다시 실행하는 방법

1. Supabase SQL Editor에서 `db/notes.sql`의 권한 줄(`grant select, insert, update, delete ... to service_role`)을 실행합니다.
2. Supabase 대시보드 Authentication > Users에서 시험 계정을 만들고, 비밀번호는 코드·Git·채팅에 적지 않습니다.
3. Vercel 환경변수 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`는 2단계에서 넣은 값을 그대로 씁니다.
4. 푸시하면 Vercel이 다시 배포합니다.

### 확인 방법

- 시크릿 창에서 배포 주소를 열면 메모가 보이지 않아야 합니다. `/api/notes`를 직접 열면 `401 LOGIN_REQUIRED`가 나옵니다.
- 시험 계정으로 로그인하면 메모를 추가·수정·삭제할 수 있어야 합니다.
- `npm run bundle`의 직접 점검은 로그인 없는 GET·POST·PUT·DELETE와 가짜 토큰이 거부되는지(상태 코드만) 기록합니다. 로그인 후 추가·수정·삭제는 비밀번호가 필요해 자동 점검에 포함하지 않았고 미실행으로 남겼습니다.

### 3단계 당시 남은 약점 (소유자 검사는 4단계에서 막음)

- 소유자 검사를 하지 않았습니다. `GET·PUT·DELETE /api/notes/:id`는 로그인한 사람이면 누구의 메모든 읽고 고치고 지울 수 있습니다. 예를 들어 B 계정이 A의 메모 id를 알면 접근할 수 있습니다. 4단계에서 소유자 검사를 붙일 예정입니다.
- 로그인 화면이 공식 SDK를 외부 배포망(jsdelivr)에서 버전을 고정해 불러옵니다.
- 옛 공개 커밋(`Initial commit`)과 1단계 때의 옛 배포에는 가상 메모가 그대로 남아 있습니다. 최신 파일에서 지웠다고 과거 노출이 해소된 것은 아닙니다.

## 4단계: 로그인해도 내 자료만 보이게 합니다 (4단계 기록)

로그인한 사람이라도 자기 메모만 읽고 추가·수정·삭제할 수 있습니다. 서버가 요청에 적힌 메모 번호를 믿지 않고, 매번 서버가 확인한 사용자 ID와 DB의 `owner_id`를 비교합니다. 이중으로, 학습 DB도 직접 접근할 때 본인 행만 허용합니다.

### 현재 작동하는 기능

- `GET /api/notes`는 내 메모만 돌려주고, `POST`는 `owner_id`를 항상 서버가 확인한 사용자 ID로 저장합니다.
- `GET·PUT·DELETE /api/notes/:id`는 `id`와 `owner_id`를 함께 조건으로 질의합니다. 남의 메모는 없는 메모와 같이 `404`로 거부하므로 그 번호가 있는지도 알 수 없습니다.
- 수정은 기존 행의 소유자가 본인일 때만 되고, 새 행의 `owner_id`도 본인 ID로 고정됩니다.
- 요청 본문에 본인과 다른 `owner_id`가 있으면 `403`으로 거부합니다. 응답 모양 `{id,title,body}`와 수정 본문 `{title,body}`는 그대로입니다.
- DB(`public.notes`): `anon`에는 권한이 없고, `authenticated`에는 SELECT·INSERT·UPDATE·DELETE만 있습니다. RLS 정책 4개가 모두 `auth.uid() = owner_id`일 때만 허용합니다(읽기·삭제는 기존 행, 추가는 새 행, 수정은 기존 행과 새 행 모두). 서버 함수는 `service_role`로 접근하며, 소유자 검사는 서버 코드가 합니다.
- 실제 경로는 `aleph.config.json`의 `allowedRoutes`와 같습니다: `GET·POST /api/notes`, `GET·PUT·DELETE /api/notes/:id`.

### 다시 실행하는 방법

1. Supabase SQL Editor에 `db/notes.sql` 전체를 붙여 넣고 Run 합니다(여러 번 실행해도 됩니다).
2. Authentication > Users에 시험 계정 둘(A, B)을 만들고, 비밀번호는 코드·Git·채팅에 적지 않습니다.
3. 기존 가상 메모를 A 소유로 연결하고 B 소유 시험 메모를 넣으려면, 계정 ID를 `auth.users`에서 이메일로 찾아 `owner_id`에 넣는 SQL을 SQL Editor에서 한 번 실행합니다(`db/notes.sql` 맨 아래 예시 참고).
4. Vercel 환경변수 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`는 그대로 쓰고, 푸시하면 Vercel이 다시 배포합니다.

### 확인 방법

- A와 B로 각각 로그인하면 자기 메모만 보이고, 각자 추가·수정·삭제가 됩니다.
- B로 로그인한 탭의 개발자 도구 콘솔에서 A 메모의 번호로 읽기·수정·삭제를 요청하면 모두 `404`, 본문의 `owner_id`를 A의 ID로 바꿔 추가하면 `403`이 나옵니다. 끝난 뒤 A 화면의 메모는 그대로입니다.
- SQL Editor에서 `has_table_privilege`로 `anon`은 네 가지 모두 `false`, `authenticated`는 모두 `true`인지 확인합니다.
- `npm run bundle`의 직접 점검은 로그인 없는 요청 5건과 가짜 토큰, 공개용 키로 DB Data API를 직접 읽기·삭제하는 요청이 거부되는지(상태 코드만) 기록합니다. 계정 비밀번호·토큰이 필요한 A/B 정상 사용과 교차 접근은 자동 점검에서 보내지 않고 미실행으로 남겼습니다.

### 4단계 당시 남은 약점 (직접 접근 길은 5단계에서 닫음)

- 로그인한 사용자(authenticated)가 자기 토큰으로 학습 DB를 직접 부를 수 있었습니다(본인 행만).
- 로그인 화면이 공식 SDK를 외부 배포망(jsdelivr)에서 버전을 고정해 불러옵니다.
- 옛 공개 커밋(`Initial commit`)과 1단계 때의 옛 배포에는 가상 메모가 그대로 남아 있습니다. 최신 파일에서 지웠다고 과거 노출이 해소된 것은 아닙니다.
- 직접 Data API로 `authenticated` 역할이 본인 행을 접근하는 경우는 자동 점검 대상이 아닙니다(심판이 재현할 수 없어 점수에서 제외).

## 5단계: 자료 요청을 서버 한곳으로 모읍니다 (5단계 기록)

브라우저의 메모 읽기·추가·수정·삭제는 모두 Vercel 서버 함수(`/api/notes`, `/api/notes/:id`)를 거칩니다. 학습 DB(`public.notes`)를 공개 키나 로그인 토큰으로 직접 부르는 길은 권한을 회수해서 닫았습니다.

### 현재 작동하는 기능

- 화면 코드(`public/index.html`)에는 Supabase 주소·키·SDK가 없습니다. 로그인(`POST /api/login`)·토큰 갱신(`POST /api/refresh`)·로그아웃(`POST /api/logout`)과 메모 요청 모두 같은 사이트의 서버 함수만 부릅니다. 서버 함수는 공식 SDK(`signInWithPassword`, `refreshSession`, `admin.signOut`)만 쓰고 비밀번호나 토큰을 직접 만들지 않습니다.

- 배포된 `/aleph.json`에 `allowedRoutes`가 함께 나옵니다(`scripts/deployment-identity.mjs`가 `aleph.config.json`의 값을 내보냅니다). 로그인·갱신·로그아웃 경로는 자료 API가 아니라서 `allowedRoutes`에 넣지 않았습니다.
- 서버 함수는 서버 전용 키(`service_role`)로 DB에 접근하고, 4단계의 로그인 검사와 소유자 검사(남의 메모 404, 소유자 변경 시도 403)를 그대로 유지합니다.
- `public.notes`에서 PUBLIC·`anon`·`authenticated`의 직접 권한을 모두 회수했습니다. 남은 것은 `service_role`뿐입니다. RLS와 정책 4개는 두 번째 방어선으로 남겨 두었습니다.
- `aleph.config.json`의 `originalApiUrl`에 쿼리 없는 원본 자료 경로(Supabase Data API의 `notes` 테이블 주소)를 적었습니다. 이 경로는 공개 키로 직접 부르면 거부되어야 합니다.
- 실제 서버 경로는 `allowedRoutes`와 같습니다: `GET·POST /api/notes`, `GET·PUT·DELETE /api/notes/:id`.

### 다시 실행하는 방법

1. Supabase SQL Editor에 `db/notes.sql` 전체를 붙여 넣고 Run 합니다(여러 번 실행해도 됩니다). 이미 만든 DB에서 권한만 거두려면 `revoke all on table public.notes from public, anon, authenticated;`만 실행해도 됩니다.
2. 시험 계정 둘(A, B)과 소유자 연결은 4단계 방법 그대로입니다. 비밀번호는 코드·Git·채팅에 적지 않습니다.
3. Vercel 환경변수 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`는 그대로 쓰고, 새로 `SUPABASE_PUBLISHABLE_KEY`(Supabase의 공개용 키)를 Production에 추가합니다. 추가한 뒤에 푸시하면 Vercel이 다시 배포하면서 새 값을 씁니다. 이름은 정확히 `SUPABASE_PUBLISHABLE_KEY`여야 합니다. 철자가 다르면 로그인 함수가 `SERVER_NOT_CONFIGURED`(HTTP 500)로 답하고, `npm run bundle`의 `wrong_password_login` 점검이 401이 아니라 500으로 기록됩니다.

### 확인 방법

- 배포 주소 첫 화면의 소스(`Ctrl+U`)에서 `sb_`, `supabase`를 검색해도 나오지 않아야 하고, `/aleph.json`에 `allowedRoutes`가 있어야 합니다.

### 6단계 당시 남은 약점 (복합 사건 추가 확인은 7단계에서 더함)

- 규칙은 기기 등록 여부 하나뿐이라 요청 방식(GET 등)이나 재인증(`stepUp`)은 따로 따지지 않습니다. 등록된 기기면 모든 확인된 요청을 허용합니다.

## 7단계: 평소와 다른 접속은 다시 확인합니다 (7단계 기록)

### 현재 작동하는 기능

- `src/decider.mjs`의 `readAccessContext()`가 판정 요청의 접속 정보를 읽습니다. 출처가 엔진이 심판의 가상 접속 사건으로 넘긴 값(`judge_fixture`)일 때만 지역·네트워크·시각·최근 사건을 읽고, 계약에 없는 이름(헤더 등)이 섞였거나 출처를 알 수 없으면 아무 값도 믿지 않습니다. 없거나 `unknown`이거나 모양이 틀린 값은 정상값으로 채우지 않고 `null`로 둡니다. `judge_fixture` 값은 실제 위치 증거가 아닙니다.
- 규칙 `step_up_required`: 등록된 기기에서 평소와 다른 시각(0~5시), 처음 보는 네트워크(`unusual`), 최근 1시간 안의 사건 건수 합계 10건 이상이 **한꺼번에** 맞을 때만 `step_up`(이유 코드 `step_up_required`)을 돌려줍니다. 지역은 근거로 쓰지 않고 `deny`도 만들지 않아서 정상 사용자를 영구 차단하지 않습니다. 이미 다시 확인한 요청(`stepUp.verified`)은 `allow`입니다. `RULE_IDS`는 `['device_registered', 'step_up_required']`이고 기기 규칙을 먼저 확인합니다.
- 위 시각·건수·창 길이는 문서에 정해진 값이 없어 제가 정한 시작값(`OFF_HOURS`, `HEAVY_READ_COUNT`, `HEAVY_READ_WINDOW_SECONDS`)이며, 운영 기준이 생기면 그 상수만 바꿉니다. 사건 종류(`kind`)는 구분하지 않고 건수만 더합니다.
- 토큰 원문을 기록하거나 출력하지 않습니다.

### 7단계 당시 남은 약점 (구역 규칙은 8단계에서 더함)

- 엔진이 `stepUp.verified`를 추가 확인 뒤에만 true로 주는지, 15분 안의 모든 로그인에 주는지는 문서에 구분이 없습니다. 후자라면 방금 로그인한 도플갱어도 통과할 수 있어 확인이 필요합니다.

## 8단계: 자료마다 갈 수 있는 구역을 나눕니다 (8단계 기록)

### 현재 작동하는 기능

## 9단계: 도플갱어를 찾고 권한을 거둡니다 (9단계 기록)

### 현재 작동하는 기능

- `src/detect.mjs`의 `detect(events)`: 가상 조회 사건 목록에서 같은 `identity.sub`의 `GET`이 어느 10분 구간(양 끝 시각 포함)에서든 120건을 넘으면 `{ action: 'propose_revocation', reasonCode: 'burst_read', subject: '해당 sub' }`를 돌려줍니다. 정확히 120건, 10분 밖으로 흩어진 조회, 서로 다른 사용자의 합산은 제안하지 않고 `{ action: 'observe' }`입니다. 여러 사용자가 넘으면 폭주가 가장 먼저 완성된 한 명만 제안합니다. 배열이 아니면 `TypeError('invalid_detection_events')`입니다.
- 입력 처리(`readEvents`): 사건 하나에서 시각(`at`)·요청 종류(`method`)·가명 사용자(`identity.sub`) 세 값만 읽고, 시간순으로 정렬합니다. 그 밖의 필드와 모양이 이상한 사건(시각이 날짜가 아니거나 `sub`가 비었거나 128자를 넘는 경우)은 읽지 않고 버립니다. 메모 내용·토큰·실명은 저장하거나 출력하지 않습니다.
- 회수 제안은 탐지 함수가 돌려주는 별도의 결과이며, `src/decider.mjs`의 허용·거부 응답 형식과 규칙은 바꾸지 않았습니다. 회수 API를 만들지 않았고 기기 권한도 바꾸지 않았습니다. 이전 단계 기능은 그대로입니다.

### 다시 실행하는 방법

```
npm run detect:test
```

### 확인 방법

1. `npm run detect:test`: 정상 30건, 10분 안에 120건, 서로 다른 사용자 각 100건, 10분 밖으로 흩어진 200건은 `통과`(관찰)이고, 121건과 200건 폭주는 회수 제안으로 `통과`가 나와야 합니다. 이 명령은 가상 사건 연습이며 실제 접속 회수나 심판 통과 증거가 아닙니다.

### 아직 남은 약점

- 운영 반 엔진이 검증한 사건을 이 함수에 전달하고 회수 제안을 집행하는 경로는 이 저장소에 연결하지 않았습니다. 실제 회수와 걸린 시간은 심판이 가상 사건을 보내 확인하며, 그 결과는 아직 알 수 없습니다.
- 이번 사건 계약에는 네트워크·지역·기기 값이 없어, "평소와 다른 네트워크와 다량 조회의 결합" 조건은 넣지 못했고 조회 폭주(`burst_read`) 하나만 탐지합니다. 지금의 `sub`는 연습용 가명 값이고, 브라우저가 보낸 사용자 번호를 신원으로 쓰지 않습니다.
- 10분 구간의 경계(양 끝 포함)와 여러 사용자가 동시에 넘을 때 한 명만 고르는 방식은 문서에 정해진 값이 없어 제가 정한 가정입니다.
- 판정기는 아직 실제 API 앞에 연결되지 않았고, 이 단계에서 `npm run bundle`의 직접 점검(`src/attack-check.mjs`)은 새로 추가하지 않았습니다.

## 10단계: 백업에서 자료실을 되살립니다 (10단계 기록)

### 현재 작동하는 기능

- 정책 차이 보기 `npm run policy:diff`: 침해 전에 검증한 안전 정책 사본(`policy/verified-policy.json`)과 지금 작업 폴더의 정책 파일을 비교해, 복원할 버전·사본 검증 결과·파일별 변경 범위를 실행 전에 보여 줍니다. 사본의 원본은 9단계 저장점 커밋 `13e3b09`이고, 목록에는 정책 파일 9개(`src/decider.mjs`, `src/resources.mjs`, `src/detect.mjs`, `src/verify-login.mjs`, `api/notes.js`, `api/notes/[id].js`, `api/_lib/notes-api.js`, `vercel.json`, 그리고 `aleph.config.json`의 정책 항목 `identityProvider`·`allowedRoutes`·`originalApiUrl`)의 지문(SHA-256)만 적습니다. 목록의 지문이 그 커밋에서 꺼낸 파일의 지문과 같을 때만 사본으로 인정하고, 목록이 없거나 형식·커밋·지문 검증에 실패하면 차이를 보여 주지 않고 중단합니다. 읽기만 합니다. 사본 목록은 `npm run policy:manifest -- 13e3b09`로 한 번 만들고, 이미 있으면 덮어쓰지 않습니다.
- 정책 되돌리기 `npm run policy:restore`: 인자 없이 실행하면 복원할 버전·바뀔 항목·확인 번호만 보여 주고 아무것도 바꾸지 않습니다. `-- --apply --confirm=<확인 번호>`로 다시 실행해야 되돌립니다. 확인 번호는 사본 커밋과 바뀔 파일들의 지금 지문으로 만들어서, 미리보기 뒤에 파일이 또 바뀌면 번호가 달라져 중단합니다. 적용할 때 사본 목록을 처음부터 다시 읽어 검증하고, 되돌린 뒤에도 다시 읽어 모든 파일이 사본과 같은지 확인합니다. 설정 파일은 정책 항목만 사본 값으로 바꾸고 단계·주소 같은 다른 설정은 지금 값을 유지합니다. 사본 목록에 없는 파일과 기존 감사 기록은 건드리지 않고, `policy/restore-audit.log` 끝에 복원 기록(파일 이름과 바뀌기 전·후 지문, 내용은 없음)을 한 줄 덧붙이기만 합니다. 학습 DB·배포 같은 실제 운영 정책에는 접속하지 않습니다.
- 메모 한 건 복원: 서비스 `notes`(Vercel 서버 함수 `api/notes/restore.js` + 학습용 Supabase), 경로 **`POST /api/notes/restore`**. 로그인한 본인의 메모 사본 한 건만 되살립니다. 본문은 정확히 `{ "id": "<메모 번호>" }` 하나만 받고, 다른 키(`owner_id`, `role` 등)가 하나라도 있으면 `400`으로 거부합니다. 소유자는 본문이 아니라 서버가 검증한 토큰에서만 얻습니다.
  - 사본은 비공개 테이블 `notes_backup`(만드는 SQL: `db/notes-backup.sql`)에 있고, 공개용 키로는 읽을 수 없으며 서버 함수만 읽습니다. 저장소에는 메모 문장이 없습니다.
  - 되살리기 전에 사본의 ID·소유자를 요청·로그인과, 사본의 무결성 해시(제목·줄바꿈·내용의 SHA-256, DB의 `content_sha256`)를 사본 내용과 대조합니다. 남의 사본·없는 사본은 `404`, 사본 내용이 해시와 다르면 `409`로 쓰지 않고 중단합니다. 현재 메모가 다른 사용자의 것이면(소유자 불일치) 덮어쓰지 않고 `409`(`note_owner_mismatch`)로 중단합니다. 본인의 메모이면 제목·내용을 사본 값으로 되돌립니다.
  - 사본은 세 번 읽어 검증합니다. 처음 읽어 ID·소유자·내용 해시를 검증하고, 쓰기 직전에 다시 읽어 처음 검증한 사본과 같은지 확인하며(다르거나 검증에 실패하면 `409 backup_verification_failed`로 쓰지 않음), 쓴 뒤에도 다시 읽어 메모의 ID·소유자·내용 해시가 그 사본과 같은지 대조합니다. 쓴 뒤 대조가 맞지 않으면 `500 restore_verification_failed`로 답하고, 이번에 고친 그 메모 한 건만 복원 전 내용으로 되돌립니다.
  - 쓴 뒤 다시 읽어 ID·소유자·내용 해시가 사본과 같은지 확인하고, 하나라도 다르면 `200`이 아니라 `500`으로 멈춥니다. 쓰기 요청의 응답(바뀐 행 수)에는 기대지 않고, 쓴 뒤 다시 읽어 확인한 결과만으로 판단합니다. 응답 본문은 `id`, `restored`(실제로 쓴 경우 `true`, 이미 사본과 같아 쓰지 않았으면 `false`), `contentSha256`(제목·줄바꿈·내용의 SHA-256) 세 값뿐입니다. 소유자·사본 정보·메모 내용은 응답에 넣지 않습니다. 다른 메모는 읽지도 쓰지도 않습니다.
  - 사본은 시험 계정 B의 메모 한 건만 만들어 둡니다(`db/notes-backup.sql`의 사본 만들기 문장에 그 메모 번호만 넣음). 사본이 없는 메모 번호(예: 다른 계정의 메모)는 복원하지 않고 `404`로 멈춥니다.
  - 복원 시도는 결과와 상관없이 `notes_restore_audit`에 한 줄씩 덧붙입니다(메모 문장은 남기지 않음). 열은 `note_id`, `owner_id`, `result`, `before_sha256`, `after_sha256`입니다. 로그인이 검증된 뒤의 시도는 성공(`restored`·`unchanged`)뿐 아니라 거부·실패(`backup_not_found`, `backup_verification_failed`, `note_owner_mismatch`, `restore_failed`, `restore_verification_failed`, `restore_unavailable`)도 남깁니다. 로그인이 없거나 POST가 아닌 요청, 입력 오류(400)는 기록하지 않습니다. 오류 응답은 `{ error }` 한 값이고, 감사 기록을 남기지 못하면 성공 응답 대신 `500`(`restore_audit_failed`), 예상 못한 오류는 `500`(`restore_unavailable`)입니다. 서버 함수에는 이 테이블과 사본을 수정·삭제하는 권한을 주지 않습니다. 이전 모양의 감사 표(`outcome`·`content_sha256` 열)가 있으면 `db/notes-backup.sql`을 다시 실행해 열 이름을 바꿉니다. 응답 헤더에는 `X-Resource-Id: notes.own`이 붙습니다.
  - 판정기(`src/decider.mjs`)와 `allowedRoutes`는 바꾸지 않았습니다. `aleph.config.json`의 `restoreRoute`에는 저장점에서 이 경로(`POST /api/notes/restore`)를 적었습니다(경로 표기 형식은 `allowedRoutes`와 같게 한 제 가정이고 문서에 정해진 값은 없습니다). `allowedRoutes`에 넣지 않은 이유는 그 목록이 침해 전 안전 정책 사본(`policy/verified-policy.json`, 9단계 저장점 `13e3b09` 기준)과 같아야 `npm run policy:diff`·`policy:restore`가 이 경로를 "바뀐 항목"으로 보지 않기 때문입니다. `src/resources.mjs`는 `restore`를 기능 이름으로 보고 자원으로 인정하지 않으므로, 판정기를 앞에 세우면 이 경로는 거부됩니다.
- 이전 단계 기능과 다른 메모·감사 기록은 그대로입니다.

```
npm run test:restore

```

### 확인 방법

1. `npm run test:restore`: 시험 통과 줄만 나오고 실패가 0이어야 합니다. 가짜 저장소로 한 로컬 연습이며 실제 배포 API나 심판 통과 증거가 아닙니다.
2. 배포 뒤, 시험 계정 B로 로그인한 탭의 개발자 도구 콘솔에서 B의 메모 번호로 요청합니다(토큰은 화면에 출력하지 않습니다).

```
const t = JSON.parse(localStorage.getItem('byteback-session')).access_token;
const r = await fetch('/api/notes/restore', { method: 'POST', headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${t}` }, body: JSON.stringify({ id: '<B의 메모 번호>' }) });
console.log(r.status, await r.json());
```

### 현재 작동하는 기능

- 설치형 웹앱: `public/manifest.webmanifest`(앱 이름 「BYTE BACK 내 자료실」, 짧은 이름 「내 자료실」, 앱 화면 모드, 아이콘 `public/icons/icon-192.png`·`icon-512.png`)를 첫 화면에 연결했습니다. 따로 설치하는 접속 프로그램은 없습니다.
- 오프라인 안내: `public/sw.js`는 오프라인 안내 화면(`public/offline.html`) 한 장만 미리 받아 두고, 화면 이동이 네트워크에 닿지 못할 때만 그 화면을 보여 줍니다. `/api/…` 요청(로그인·메모·복원·기기)은 가로채거나 저장하지 않습니다. 첫 화면에서도 연결이 끊기면 오프라인 안내 줄이 나옵니다.
- 기기 승인 상태 표시: 첫 화면의 「이 기기의 승인 상태」 칸이 서버 승인(미등록·승인 대기·승인됨·회수됨)과 앱 설치 여부를 따로 보여 줍니다. 앱으로 설치했거나 앱 화면으로 열었다는 사실은 승인에 쓰지 않고 서버로 보내지도 않습니다.
- 기기 승인 흐름: `GET /api/device`는 이 브라우저의 승인 상태를, `POST /api/device`는 승인 요청을 처리합니다(둘 다 로그인 필요). 승인 요청은 기기를 `승인 대기`로 등록하고 확인 코드(예: `7120-9F4C`)를 보여 줄 뿐 권한을 주지 않습니다. 관리자가 Supabase SQL Editor에서 그 확인 코드로 `approved`로 바꿔야 승인됩니다(`db/devices.sql` 아래 예시). 서버 함수는 DB 권한상 `devices` 표에 읽기와 세 열(`owner_id`, `token_sha256`, `code`) 넣기만 할 수 있어 스스로 승인할 수 없습니다.
- 기기 증표: 서버가 만든 무작위 값이며, 브라우저에는 자바스크립트가 읽을 수 없는 쿠키(`__Host-byteback-device`, HttpOnly·Secure·SameSite=Strict)로만 둡니다. localStorage·sessionStorage·IndexedDB에는 넣지 않고, DB에는 그 값의 SHA-256 지문만 저장합니다. 증표는 로그인한 사용자에게 묶여, 다른 계정으로 로그인하면 같은 브라우저라도 `미등록`입니다.
- 승인 전 자료 차단: 화면은 서버가 `승인됨`이라고 답하기 전에는 메모를 요청하지도 표시하지도 않습니다. 서버도 메모 경로(`/api/notes`, `/api/notes/:id`, `/api/notes/restore`)에서 학생 로그인의 기기 승인을 확인해, 승인 전에는 `403 DEVICE_NOT_APPROVED`로 거부합니다. 승인된 기기에서는 앞 단계의 소유자 검사(남의 메모 `404`, 소유자 변경 `403`)와 복원 규칙이 그대로입니다.
- 심판 로그인(심판 발급자의 ES256 서명 토큰)은 브라우저 기기 쿠키가 없는 가상 요청이라 이 기기 검사를 건너뜁니다. 심판 쪽 기기 확인은 운영 엔진이 따로 한다는 `docs/DECIDER_REQUEST.md`의 `deviceRegistered` 설명을 근거로 한 제 가정입니다.
- 10단계 정책 사본(`policy/verified-policy.json`)은 이번 저장점 커밋 기준으로 다시 만들었습니다(메모 API에 기기 검사가 들어갔기 때문). 이전 단계 기능과 다른 메모는 그대로입니다.

### 다시 실행하는 방법

1. Supabase SQL Editor에서 `db/devices.sql`을 한 번 실행합니다(여러 번 실행해도 됩니다). 새 환경변수는 없습니다.
2. 배포 주소에서 로그인한 뒤 「이 기기 승인 요청」을 누르고, 나온 확인 코드로 SQL Editor에서 아래를 실행합니다.

```
update public.devices set status = 'approved', approved_at = now() where code = '<확인 코드>' and status = 'pending' returning code, status;
```

3. 화면에서 「승인 상태 다시 확인」을 누르면 자료실이 열립니다. 회수는 `update public.devices set status = 'revoked' where code = '<확인 코드>';`입니다.

### 아직 남은 약점

- 로그인 토큰(접속 토큰·갱신 토큰)은 아직 브라우저 저장소(`localStorage`의 `byteback-session`)에 있습니다. 기기 증표는 쿠키로만 두지만, 로그인 토큰을 HttpOnly 쿠키로 옮기는 일은 하지 않았습니다.

- 한 브라우저에는 기기 증표가 하나라서, A가 승인받은 브라우저에서 B가 승인을 요청하면 증표가 B 것으로 바뀌어 A는 다시 요청해야 합니다.
